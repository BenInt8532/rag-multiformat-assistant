# RAG-ассистент по документам разных форматов

Консольный ассистент, который отвечает на вопросы по папке с документами: PDF, DOCX, XLSX, CSV, HTML, Markdown, TXT и файлам с кодом Python. Главная идея проекта: каждый файл режется на чанки своим способом, а способ задаётся одной строкой в текстовом файле `chunking.txt`.

В комплекте учебная база из девяти документов вымышленной партнёрской сети «ЛидПоток» и набор проверок, которыми подбирались настройки.

## Что умеет

- Читает восемь форматов и убирает из текста мусор: меню и подвал страниц HTML, колонтитулы и переносы PDF.
- Режет каждый файл по своему правилу: FAQ по парам «вопрос и ответ», таблицу по строкам с названиями столбцов, код по функциям, инструкцию без разрыва списков.
- Отвечает только по найденным фрагментам. Если ответа в документах нет, говорит об этом одной и той же фразой и ничего не додумывает.
- Показывает, из каких файлов взят ответ, какие чанки нашёл поиск и сколько токенов потрачено.
- Не считает повторно то, что уже посчитано: векторы и ответы лежат в кешах.

## Установка и запуск

Нужен Python 3.13 и ключ OpenAI. Проект проверен на версии 3.13. На Python 3.14 на момент проверки (октябрь 2026) не устанавливалась библиотека оценки `ragas` версии 0.4.3: её зависимость `scikit-network` не имела готовой сборки под 3.14, а сборка из исходников завершалась ошибкой.

Команды для PowerShell, из папки проекта:

```powershell
py -3.13 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item env.example .env
```

Откройте `.env` и впишите свой ключ в строку `OPENAI_API_KEY`. Остальные настройки необязательные, у каждой есть значение по умолчанию.

Запуск:

```powershell
python app.py
```

При первом запуске ассистент прочитает папку `data`, нарежет документы и соберёт базу. Дальше база пересобирается, только если изменились документы или правила нарезки.

Команды в чате: `stats` (сведения о базе и кешах), `clear` (очистить кеш ответов), `exit` (выход).

Чтобы подключить свои документы, положите их в папку `data` и добавьте для каждого строку в `chunking.txt`.

## Как устроено

Путь вопроса:

```
вопрос
  │
  ▼
кеш ответов ── такой вопрос уже был ──► готовый ответ
  │ нет
  ▼
поиск по базе (ChromaDB) ──► кандидаты: самые похожие чанки
  │
  ▼
отбор в контекст (три фильтра, см. ниже)
  │
  ├── не прошёл ни один чанк ──► «В документах нет информации по этому вопросу.»
  │                               модель не вызывается
  ▼
модель (gpt-4o-mini) + промпт с правилами ──► ответ и номера фрагментов
  │
  ▼
номера фрагментов переводятся в имена файлов ──► «Ответ взят из: ...»
```

Файлы:

| Файл | За что отвечает |
|---|---|
| `app.py` | чат в консоли: ввод вопроса, печать ответа и найденных чанков |
| `assistant.py` | путь вопроса целиком: кеш, поиск, отбор контекста, вызов модели |
| `prompts.py` | тексты промптов и разбор строки «Источники» |
| `loaders.py` | чтение форматов и очистка текста |
| `chunking.py` | способы нарезки |
| `index.py` | база чанков с векторами в ChromaDB |
| `config.py` | чтение `.env` и `chunking.txt` с понятными сообщениями об ошибках |
| `chunking.txt` | правила нарезки, по строке на файл |

### Сколько чанков получает модель

Настройка `TOP_K` здесь означает потолок, а не количество. Чанки проходят три фильтра по порядку:

```
кандидаты из поиска
   │
   ├─ 1. порог схожести (SCORE_THRESHOLD=0.2)  слабо похожие отбрасываются
   ├─ 2. бюджет контекста (CONTEXT_BUDGET=2000) лучшие набираются, пока помещаются по символам
   └─ 3. потолок (TOP_K=8)                      больше восьми не берётся
```

Почти всегда первым срабатывает бюджет. Длинных абзацев в контекст входит два-три, коротких строк таблицы до восьми. Число чанков зависит от их размера, поэтому главный ограничитель задан в символах, а не в штуках.

Значения подобраны на учебной базе из девяти файлов. На большой базе их стоит перепроверить.

## Правила нарезки

Файл `chunking.txt` читается построчно:

```
имя файла : способ, параметр=значение, параметр=значение
```

| Способ | Как режет | Для чего подходит |
|---|---|---|
| `fixed` | по числу символов, не глядя на смысл | точка отсчёта для сравнения |
| `paragraphs` | по абзацам, длинный абзац по предложениям | связный текст |
| `sections` | по разделам, заголовок в начале каждого чанка | документ с заголовками |
| `qa` | вопрос и ответ в одном чанке | FAQ |
| `lists` | как `paragraphs`, но список не разрывается | инструкции с шагами |
| `table_rows` | строка таблицы в одном чанке вместе с названиями столбцов | таблицы |
| `code` | функция или класс в одном чанке, с подписью «файл, функция» | код |

Параметры: `size` (размер чанка в символах), `overlap` (перекрытие соседних чанков), `merge=no` (каждый абзац отдельным чанком, для `paragraphs`), `consts=yes` (к чанку функции дописываются настройки из начала файла, которыми она пользуется, для `code`).

Решётка в начале строки выключает файл: в базу он не попадает. Файл без своей строки в базу тоже не идёт.

Режим `CHUNKING_MODE=uniform` в `.env` режет все файлы одним правилом. Он нужен для сравнения: насколько правила по файлам лучше единой нарезки.

## Для проверки

Эта часть нужна тому, кто меняет нарезку или промпт. Для работы чата она не требуется.

Проверки делятся на два типа. Проверки без ключа бесплатные и занимают секунды: они отсеивают грубые ошибки до того, как тратить деньги и время на проверки с ключом. Проверки с ключом обращаются к OpenAI, стоят центы и идут минуты: они показывают качество ответов.

| Скрипт | Ключ | На какой вопрос отвечает | Когда запускать |
|---|---|---|---|
| `tests/test_offline.py` | нет | не сломан ли код: чтение файлов, очистка, нарезка, файл правил, кеши | после любой правки кода |
| `tests/report_traps.py` | нет | попали ли нужные куски текста в один чанк при единой нарезке и при нарезке по правилам | после смены правила нарезки |
| `tests/run_online.py` | да | работает ли цепочка целиком: сборка базы, контрольные вопросы, кеш, отключение файла, порог | после установки и крупной переделки |
| `evaluate_ragas.py` | да | сколько вопросов из набора закрыто и как ответы оценил судья | для сравнения двух настроек |
| `tests/tune_file.py` | да | какое из нескольких правил лучше для одного файла | при подборе нарезки под файл |

Запуск:

```powershell
python -m unittest tests.test_offline -v
python tests/report_traps.py
python tests/run_online.py
python evaluate_ragas.py
python tests/tune_file.py --full-base --repeats 2 vyplaty-i-hold.pdf "paragraphs, size=800, overlap=150" "sections, size=900"
```

### Как работает оценка (`evaluate_ragas.py`)

```
eval/questions.json                      ассистент с рабочими настройками
(вопрос, эталон, нужный файл)                        │
        │                                            │
        ▼                                            ▼
1. задаёт вопросы по одному, получает ответ и найденные чанки
        │
        ├─► 2. считает без модели: найден ли нужный файл и на каком месте,
        │      отказ это или ответ, на какой файл сослалась модель
        │
        ├─► 3. отдаёт судье (вторая модель, библиотека RAGAS):
        │      Faithfulness       всё ли в ответе подтверждено чанками
        │      Context Precision  нужные ли чанки нашёл поиск
        │      Answer Relevancy   по делу ли ответ
        ▼
4. сохраняет ответы, чанки и оценки в results/<дата>-...-ragas.json
5. печатает средние, разбивку по файлам и по типам вопросов
```

Три вида проверки ловят разное:

| Что случилось | Чем ловится |
|---|---|
| поиск принёс не тот файл | счётчик попадания (шаг 2) |
| поиск принёс нужное, модель добавила своё | Faithfulness (шаг 3) |
| оценка судьи хорошая, а ответ неверный | чтение ответов в сохранённом файле (шаг 4) |

Что важно знать про оценки:

- Счётчики из шага 2 при повторе не меняются. Оценки судьи между одинаковыми прогонами немного отличаются, поэтому малой разнице между двумя прогонами верить нельзя.
- Отказы на Faithfulness не отдаются и считаются отдельно: верные (вопрос не по базе) и ошибочные (ответ в базе был). В отказе нечего сверять с чанками, судья ставит за него ноль, и среднее перестаёт показывать то, для чего придумано.
- Answer Relevancy на этой базе ненадёжна: один и тот же верный ответ получал в разных прогонах и 0, и 1. В выводах она не используется.
- Число метрики всегда сверяется с самим ответом.

### Как работает подбор правила (`tests/tune_file.py`)

```
файл + правило А + правило Б + правило В
              │
   ┌──────────┼──────────┐
   ▼          ▼          ▼
база с А   база с Б   база с В     меняется нарезка одного файла,
   │          │          │         остальные файлы как в chunking.txt
   ▼          ▼          ▼
все вопросы набора, счётчики и судья
   │          │          │
   └──────────┼──────────┘
              ▼
   таблица: правила рядом
```

- Флаг `--full-base` оставляет в базе все документы. Так чанки файла соревнуются с чанками остальных документов, как в настоящей работе. В базе из одного файла поиску не с чем его перепутать, и близкие правила выглядят одинаково хорошими.
- Флаг `--repeats N` прогоняет каждое правило несколько раз. Это отделяет настоящую разницу между правилами от разброса оценок судьи.
- Файл `chunking.txt` скрипт не меняет. Лучшее правило переносится в него вручную.

### Два набора вопросов

| Файл | Вопросов | Назначение |
|---|---|---|
| `eval/questions.json` | 24 | на них подбирались нарезка и промпт |
| `eval/questions-proverka.json` | 29 | проверочный: составлен после всех правок, под него ничего не подбиралось |

Что заложено в документы базы и каким вопросом это проверяется, описано в `eval/karta-lovushek.md`.

Настройки, подобранные на наборе вопросов, на этом же наборе выглядят лучше, чем есть. Поэтому итоговая цифра берётся с проверочного набора, а сам он не используется для правок.

Другой набор вопросов и другой файл правил задаются переменными окружения на один запуск, рабочие файлы при этом не меняются:

```powershell
$env:QUESTIONS_FILE = "questions-proverka.json"
python evaluate_ragas.py
Remove-Item Env:QUESTIONS_FILE
```

`QUESTIONS_FILE` это имя файла в папке `eval`, `CHUNKING_FILE` это имя файла правил в папке проекта.

## Результаты

Проверочный набор, 29 вопросов (26 по базе и 3 не по базе). Настройки одинаковые, отличается только нарезка. Ответы сверены с эталоном вручную.

| Показатель | Единая нарезка | Нарезка по правилам |
|---|---|---|
| Верных ответов | 20 из 29 | 25 из 29 |
| Нужный файл найден | 22 из 26 | 25 из 26 |
| Ошибочных отказов | 6 | 1 |
| Отказы на вопросах не по базе | 3 из 3 | 3 из 3 |
| Токены запросов, всего | 24640 | 24808 |

Что показала проверка:

- Правила по файлам дают больше верных ответов при том же расходе токенов.
- Выигрыш приходит от FAQ, таблиц и кода. Для связного текста (PDF, правила, инструкция, глоссарий) обе нарезки ответили одинаково.
- Чанк должен быть понятен без соседей. Функция, в которой стоит только имя настройки, бесполезна без её значения; после приписки настроек к функции вопросы по коду закрылись.
- Крупные чанки для кода вредят: файл перестаёт находиться. Работает нарезка по функциям с подписью «файл, функция».

## Известные ограничения

Четыре вопроса проверочного набора остались без верного ответа. Нарезкой они не исправляются.

| Тип вопроса | Что происходит | Причина |
|---|---|---|
| ответ складывается из двух условий в разных разделах | модель называет одно условие | оба были в контексте, модель их не объединила |
| вопрос в два шага: нужное сведение в вопросе не названо | модель пересказывает правило без вывода | поиск по сходству не находит абзац, о котором в вопросе нет слов |
| нужен небольшой вывод из текста («товарные» входят в «остальные вертикали») | отказ | промпт требует отвечать только прямо написанным |
| «перечисли всё» по таблице | ответ неполный | поиск приносит часть строк, а не все |

Отказ в третьем случае оставлен намеренно. Если ослабить правило, лишних отказов станет меньше, а выдуманных ответов больше. Для ассистента по документам отказ безопаснее уверенной ошибки.

Остальное:

- Проверено на базе из девяти небольших файлов и на модели `gpt-4o-mini`.
- Параметр `consts=yes` приписывает к функции настройки, которые объявлены в начале файла (например, `MIN_VISITS = 150`). Проверен на файлах, где код состоит из отдельных функций. На коде с классами не проверялся: настройки, объявленные внутри класса, он может не найти.
- Проверки с ключом запускаются строго по одной. Все они работают с одной базой чанков в папке `chroma_db` и перед началом перестраивают её под свои настройки. При двух запусках одновременно один перестроит базу, пока другой задаёт вопросы, и результаты второго окажутся от чужой нарезки. На обычную работу чата это не влияет.
